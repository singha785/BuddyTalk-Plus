Goals
1. Forgot Password flow
Add a "Forgot Password?" link on the login screen.
New screen: user enters email (or phone, see OTP section) → triggers a reset code/link.
If a backend already exists (check api-server or server/ folder for auth routes), wire this to a real endpoint (e.g. POST /auth/forgot-password, POST /auth/reset-password). Add a simple password strength indicator on signup (weak/medium/strong) based on length + character variety — no external dependency needed, a small local utility function is enough.
3. Dual login: Email OR Mobile OTP
On both Login and Signup, add a segmented toggle/tab: "Email" vs "Phone".
Phone flow:
User enters phone number (with country code picker if not already present — check if libphonenumber-js or similar is installed; if not, a simple default-country-code approach is fine for now).
"Send OTP" button → calls backend to trigger SMS OTP (need an SMS provider — check if Twilio/MSG91/Firebase is already configured anywhere in api-server; if not, stub the endpoint clearly with a TODO: plug in SMS provider comment so I can add API keys later).
6-digit OTP input (use segmented OTP input boxes, not a single field — check if a package like react-native-otp-entry or similar exists already; if not, add a lightweight custom component, don't pull in a heavy dependency).
Verify OTP → on success, log in / complete signup same as email flow (same JWT/session mechanism already used for email auth — reuse it, don't create a parallel auth system).
4. OTP Auto-read / Autofill

This is Expo managed workflow, so implement it the correct way for that constraint:

iOS: use textContentType="oneTimeCode" on the OTP TextInput(s) — this enables the native QuickType autofill suggestion above the keyboard automatically. No extra library needed.
Android: true SMS auto-read (without user tapping anything) requires either:
The SMS Retriever API (needs a formatted SMS with an app hash code, and typically needs a config plugin / native module — react-native-otp-verify is the common library, but confirm it has an Expo config plugin or works with a dev client build, since this project uses EAS builds already, that's fine).
OR the simpler SMS User Consent API which just needs RECORD_SMS-free permission (no runtime permission prompt) and pops a system dialog asking the user to allow autofill — this is less invasive and preferred if available in whatever library gets used.
Add the required permission(s) to app.json under android.permissions if the chosen library needs one (e.g. RECEIVE_SMS for SMS Retriever), and add the necessary config plugin entry.
Make sure this is optional/graceful — if autofill fails or isn't supported on a device, the user must still be able to type the 6-digit code manually.
